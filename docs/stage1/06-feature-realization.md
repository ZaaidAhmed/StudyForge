# Stage 1 - Feature Realization

This document explains how the design components collaborate. Names are planned contracts and must remain synchronized with implementation.

| Feature | Related Use Case | Related Sequence Diagram | Classes and responsibilities | Important methods / execution | Pattern involvement |
|---|---|---|---|---|---|
| F01 | UC01 | UC01 CRUD flow; no separate multi-step sequence required | `CourseController` maps forms; `CourseService` validates and coordinates; `CourseRepository` persists. | `createCourse`, `updateCourse`, `findByCode` validate and persist course data. | MVC, Repository |
| F02 | UC02 | SD01 | `MaterialController` accepts web uploads and material CLI commands call `StudyAgentFacade`; `CourseMaterialService` owns the workflow; `DocumentValidator`, `HashService`, `FileStorageService`, extractor factory/extractors, `TextNormalizer`, `TextChunker`, and repositories perform focused steps. | `importMaterial` validates, hashes, deduplicates by course/hash, stores safely, extracts, normalizes, chunks, and persists `CourseDocument`/`DocumentChunk` records. | MVC, extractor polymorphism, Repository |
| F03 | UC03 | SD08 | `MaterialController` and `MaterialSearchCommand` call `StudyAgentFacade`; `CourseSearchService` validates the course/query, loads only READY course chunks, scores and ranks them, applies threshold/top-K, and maps source-aware `SearchResult` DTOs. | `search` normalizes the query, uses `LexicalRetrievalScorer`, applies deterministic tie-breaking, and preserves document/chunk/page metadata. | MVC, Repository |
| F04 | UC04 | SD02 | `AgentController` and `StudyAgentFacade` enter the workflow; coordinator/planner select retrieval; search tool retrieves; `QuestionAnsweringService` prompts LLM and records history. | `ask`, `coordinate`, `askQuestion` validate relevance and source IDs before returning an answer. | Facade, Command, Adapter |
| F05 | UC05 | SD02 shared grounded AI path | `SummarizationService` bounds and combines source sections; `PromptBuilder` and `LlmClient` provide AI wording; source metadata remains attached. | `summarize` retrieves, calls the adapter, parses structured sections, and returns sources. | Adapter |
| F06 | UC06 | SD02 shared retrieval/AI path | `ConceptTool` obtains context; `ConceptService` and `StructuredResponseParser` validate, deduplicate, and persist concepts. | `extractConcepts` and `parseConcepts` reject invalid source IDs and names. | Command, Adapter |
| F05 | UC05 | bounded grounded AI path | `SummarizationService` validates document ownership/readiness, preserves chunk order, bounds context, parses structured output, and maps StudyForge-owned sources. | `summarizeDocument` and `summarizeTopic`; topic no-evidence skips `LlmClient`. | Adapter |
| F06 | UC06 | bounded grounded AI path | `ConceptExtractionService` parses structured concepts, validates source IDs, and merges normalized duplicate names deterministically. | `extract`; request-based result because no concept persistence schema exists yet. | Adapter |
| F07 | UC07 | grounded generation plus deterministic review | `FlashcardGenerationService` bounds persisted document chunks, calls provider-neutral AI, validates/deduplicates cards, and persists relational provenance. `FlashcardReviewService` validates ownership/rating and appends review events without AI. | `generate`, `list`, `review`. | MVC, Adapter |
| F07 | UC07 | SD07 | `FlashcardService` retrieves context, generates sourced cards, persists them, and records review attempts; controller renders review. | `generateFlashcards` and `recordReview` are separate generation/review operations. | Adapter, Repository |
| F08 | UC08 | SD03 | `QuizGenerationTool` loads weak-topic progress when needed; search supplies context; `QuizService` parses and validates structured questions before persistence. | `generateQuiz` performs one controlled retry for invalid model output. | Facade, Command, Adapter |
| F09 | UC09 | SD04 | `QuizService` delegates scoring to `GradingService`, stores `QuizAttempt`, and publishes `QuizCompletedEvent`. | `submitQuiz` and `grade` produce deterministic results; `QuestionResponse` records each response. | Observer, Repository |
| F10 | UC10 | SD02 shared grounded AI path | `QuestionAnsweringService` supplies question, response, rubric, and evidence; adapter returns labeled AI-assisted feedback. | `explainMistake` validates sources and never stores hidden model reasoning. | Adapter |
| F11 | UC11 | SD04 and SD06 | `ProgressUpdateListener` reacts to quiz completion; `ProgressService` calculates scores and weak topics; tools expose state to the agent. | `updateProgress` and `findWeakTopics` distinguish no-data from weak performance. | Observer, Repository |
| F12 | UC12 | SD05 | `StudyPlanService` loads progress, `WeakTopicAnalyzer` prioritizes, selected `StudyStrategy` allocates, and `Scheduler` enforces hard constraints. | `createPlan`, `allocate`, and `schedule` persist only valid `StudyActivity` items; LLM wording cannot change timing. | Strategy, Facade |
| F13 | UC13 | SD06 | `ProgressTool`, `StudyPlanTool`, and `HistoryTool` provide state; `RecommendationService` decides the next action. | `recommendNextStep` combines weak areas, plan, and recency before responding. | Command, Facade |
| F14 | UC14 | SD02 and SD06 | `LearningHistoryService` stores bounded observable requests, tools, outcomes, and sources; `HistoryTool` retrieves relevant records. | `recordSession` and `findRelevantHistory` support adaptation without storing hidden reasoning. | Command, Repository |

## Final code reconciliation

The historical rows above retain the original Stage 1 design vocabulary. For the delivered implementation, the authoritative realizations are the concrete services and DTOs listed in `05-feature-traceability.md` under “Final implementation reconciliation”; notably, F08–F10 use `QuizGenerationService`, `QuizAttemptService`, and `WrongAnswerExplanationService`, while F11–F14 use deterministic `ProgressService`, `StudyPlanService`, `RecommendationService`, and `LearningHistoryService`.
